# 开机站立与遥控运行程序 0.1.12

当前源码为 **0.1.12 禁能过渡修复候选，尚未切换运行或实物验证**。树莓派有
现场采用记录的是 0.1.10。0.1.11 离线安装检查已通过，但切换前核对实车停止
报文发现：首个禁能回复可仍显示先前 mode 1，随后才确认 mode 0；0.1.11
会把这次正常过渡锁止，因此未启动。0.1.12 区分首次回复的原运动状态与
后续禁能确认，通信、温度、电压、错误位等仍严格检查，行驶参数与主动阈值不变。

这是独立的可行性验证车运行程序，基于冻结的 v184 控制源码；不修改
`control/source_manifest.json` 或正式 STM32 项目。尚未获得长期实物可靠性验证。
部署、离线检查与有限现场结果见[验证记录](VALIDATION.md)。

## 使用流程

1. 上电后 systemd 启动 `mori-balance.service`，等待 USB 模块就绪。
2. 电机保持禁能。两轮着地，将车身扶到直立、上层平台接近水平；俯仰在
   原 v184 的 ±10° 内、横倾在 ±5° 内，轮子基本静止、角速度较低，连续保持 **1.5 秒**。
   期间偏离条件或按住方向键会重新计时。不是从躺倒姿态自行起身。
3. 通过原有零指令接管检查后持续站立，沿用红点和一声提示。
   没有 30 秒等待超时或 30 分钟试验结束；不会周期重启控制器。
4. 小米蓝牙遥控器 2 Pro：上/下为前进/后退，左/右为转向；按住持续，
   松开减速后就地站立。确认或返回停止行驶、保留平衡。
   遥控器休眠不阻止站立；断连或输入工作线程失效时行驶参考回零。
   重连后须先松键。原 evdev 排他抓取保持，站立服务运行时遥控器由它使用。
5. **先扶住车身，再同时按住确认和返回约 1 秒**，可主动禁能并锁止；
   此操作会退出平衡。也可扶住后执行 `systemctl stop mori-balance`。

原 v184 站立姿态 PID 和扭矩预算保持，没有自动调参或参考脉冲。
0.1.1 按现场反馈将前后起步的参考平滑时间由 0.20 秒缩短到 0.12 秒；
最高参考速度仍为 ±0.12 m/s、参考加速度上限仍为 0.30 m/s²。
松键和反向制动阶段仍用原 0.20 秒平滑；这些是控制参考，不是实测地速。
0.1.3 在按住前/后键、参考与意图同向时，把行驶速度反馈增益从 0.35
提高到 0.50、目标倾角变化上限从 6 提高到 9°/s，仍限制在 ±3° 内。
松键、纯转向、反向制动和站立保留原路径。左右转向参考的加速上限由
6 改为 12 rad/s²，目标轮速差仍为 ±4 rad/s，松键/反向制动仍用 6。
0.1.5 将前后最高参考提高到 ±0.16 m/s，起步平滑时间 0.08 秒、
加速度上限 0.40 m/s²，行驶目标倾角变化上限 12°/s；行驶增益仍 0.50、
倾角上限仍 ±3°。转向目标轮速差 ±5 rad/s、加速上限 16 rad/s²。
松键/反向制动仍用 0.20 秒与 0.30 m/s²，转向制动仍 6 rad/s²。
组合输入及切换方向时按 `abs(v)/名义轮半径 + abs(轮速差)/2 ≤ 5 rad/s`
分配参考余量，优先允许减速，且保留各轴变化率限制；不提高实际轴速
6 rad/s 停止线或 0.12 N·m 软件扭矩预算。最高参考不等于实测最高车速。
物理方向由操作者确认：上键朝蓝点一侧，下键反向。
保留温度、姿态、速度、力矩估计、IMU/反馈截止时间和双轮停机确认。
沿用已做禁能通信对照的 `accepted_write.py`：完整包交给内核后立即返回，
仍受原 8 ms 写入/反馈期限约束；内核接收不等于电机已收到。

## 倒下后重新进入平衡

0.1.8 保持 0.1.5 的行驶参数。已进入主动平衡后，姿态过大、角速度过大或
轮速超限仍先立即停机。只有双轮禁能与停止均确认、两轮健康反馈正常、
停止期间没有通信/传感器错误时，才进入重新扶正等待，不重启服务或电源。

- 程序需在双轮停稳后看到车身偏离扶正范围至少 0.25 秒。现有停止后
  IMU 观察记录若已满足该条件，也可作为依据；这能避免扶起较快时要求再倾斜。
- 接着两轮着地、车身扶正、松开全部按键，完整稳住 1.5 秒后重新接管。
  每轮使用新控制器，清空速度/转向目标、积分、位置和航向原点。
- 若只是超速停机、车身一直直立，程序提示先倾斜再扶正，不会反复自行启动。
- 已确认的通信/采样时序异常、过温、错误位、停止未确认、主动禁能等仍锁止；
  不把所有故障都当作倒下。
- 0.1.9 允许在已健康停稳并保存记录的恢复交接中，确认清除禁能空闲期间
  产生的驱动超时标记。该操作仅限下一轮最初的 mode 0 握手：错误位、温度、
  电压等检查必须通过，清除后必须重新查询确认；随后完整扶正计时不变。
  扶正等待、使能过渡和主动平衡中的超时不会因此获得重试或自动清除。

0.1.10 区分“电机已禁能”和“轮子已静止”：对符合恢复条件的运动停机，
若已经连续确认两轮 mode 0 且健康，只是扶车/滑行导致轮子尚未停稳，
继续发送禁能查询并等待三对连续静止反馈，不再因原有限试验的一秒期限退出。
这段等待不会发送使能命令；禁能不确认或通信、传感器、健康异常仍终止恢复。
倾倒姿态已记录且反馈无错误位的瞬时扭矩超限，也可在健康停稳后进入上述流程；
直立时的过载、持续扭矩超限仍锁止。原扭矩停止阈值及行驶参数不提高。

0.1.11 为停止期间的每次通信/健康检查异常累计不可清除的计数，并保存首次
异常及最多 32 条末段详情。后续正常反馈可以确认已禁能、已停稳，但不能
抹掉异常或允许自动恢复；正常停止请求期间遇到这些异常也保留持久锁止。
每轮结束均移除临时遥测回调，避免暂停循环垃圾回收时控制器和报告累积。

0.1.12 允许第一条禁能命令的回复仍为原 mode 1，但这条回复不计入禁能
确认；之后必须取得连续 mode 0 和静止反馈。首次回复的过温、错误位、
超时等仍会锁止，后续确认阶段的 mode 1 也不能被健康回复抹掉。
只有原本符合运动恢复条件的停机，其首次 mode 1 回复中的残留速度/扭矩
才单独记录为尚未禁能的运动状态；后续 mode 0 中的运动越限仍是锁止故障。

每次可恢复运动停机的原始有界结果保存于 `/var/lib/mori-balance/motion-stops/`。
归档失败也不会再次使能。0.1.10 已有一次手扶倾倒停机后，无断电、无服务重启再次接管的现场确认；
具体记录见验证文档，长期及其他故障场景仍需分别验证。

## 故障及复位

0.1.2 在尚未发送任何使能包的等待阶段，允许丢弃偶发迟到/缺失反馈或
过期 IMU 样本，并重新取得新鲜数据和完整 1.5 秒扶正计时。连续 5 次
失败仍锁止。不是对已经运行或故障停机的平衡控制自动重启。
0.1.7 将禁能等待阶段的偶发 `imu_sample_gap` 纳入同一有限恢复路径：
丢弃该帧并重置估计器与扶正计时；重复间断无法完成扶正计时，不能使能。
使能过渡及主动平衡阶段的采样间隔保护不变，异常仍停机锁止。
实时状态会显示俯仰、横倾、轮速、稳定计时和窗口摆动幅度。

0.1.6 保留 0.1.5 的全部行驶参数，增加操作者明确要求的直接断电后再上电启动：

- 正常停机且确认双轮禁能后，下次启动进入扶正等待。
- 如果只留下“运行未结束”标记，且 Linux 内核启动 ID 已改变，先原样归档
  上次标记，再重新执行设备检查、禁能反馈检查、松键和完整 1.5 秒扶正等待。
  不恢复旧速度、方向或累计扶正时间。该标记不能证明中断一定由断电引起。
- 已记录且未满足上述运动恢复条件的故障，包括通信异常、超温、主动禁能
  或停止未确认，仍持久锁止，重新上电不清除。未知、损坏或不带启动 ID 的旧标记也不自动恢复。
- 同一次系统启动中的进程异常退出仍锁止，systemd 不自动重启。

首次启动及已验证运动停机后的恢复交接，仅在最初的 mode 0 握手中可确认
并清除空闲通信超时标志；等待、使能过渡和主动平衡中的故障不自动清除。
重新使能须满足上文全部恢复条件。mode 0 是协议禁能，不等于物理断电。直接切电测试由操作者
扶稳车身后执行；文件系统抗断电能力及反复冷启动可靠性尚未验证。

```sh
systemctl status mori-balance --no-pager
cat /run/mori-balance/status.json
journalctl -u mori-balance -n 30 --no-pager
cat /var/lib/mori-balance/latch.json
# 接住/支撑车身、检查故障原因后：
systemctl stop mori-balance
python3 /opt/mori-balance/current/runtime/reset_fault.py --car-supported
systemctl start mori-balance
# 取消开机启动（先扶住）：
systemctl disable --now mori-balance
```

状态文件含单调时钟时间；进程退出后不会更新，不将旧状态当作当前姿态。
最后结果在 `/var/lib/mori-balance/last-result.json`，仅保留最近 400 个控制
样本、100 个等待样本及每轮 1000 条串口事务。它们是故障附近的片段，
不是完整高频记录；原试验日志不受影响。

## 当前开机服务组合

调试时已停止的旧 `mori-person.service` 和 `mori-realtime.service` 已设置为
不开机启动，原配置保留。冷启动发现遥控语音服务仍通过 `Wants=` 拉起
`mori-realtime`；因此额外安装 [启动条件](legacy-realtime-isolation.conf) 到
`/etc/systemd/system/mori-realtime.service.d/90-balance-isolation.conf`，
在显式创建 `/etc/mori-realtime.allow-start` 前跳过旧桥接启动。
其余语音服务及配置保留。禁用这两项服务并不证明它们是采样延迟根因。

## 安装与验证

安装包包含 `runtime/` 和原样 `control/`，使用独立版本目录及 `current`
链接，现场标定单独保留。配置记录基础源码清单、运行源码清单、标定的
SHA-256；任何不匹配均拒绝打开硬件。服务文件见 `mori-balance.service`。
不把私人标定、设备状态或凭据提交到仓库。

Python 3.12+；实机依赖 pyserial 3.5、smbus2、evdev、BlueZ 和原 CAM
显示固件。以下从仓库根目录执行，测试使用假 IMU/总线，绝不驱动硬件：

```sh
PYTHONPATH=test_rig/runtime:test_rig/control:test_rig/control/tests \
  python3 -B -m unittest discover -s test_rig/runtime/tests -v
(cd test_rig/control && python3 -B -m unittest discover -s tests -q)
python3 test_rig/tools/check_release.py
# 安装后的文件与标定校验，不打开设备：
python3 /opt/mori-balance/current/runtime/main.py --check --config /etc/mori-balance.json
```

串口候选的两个匿名管道回归需要 Linux `os.pipe2`。启动状态机覆盖扶正
计时中断、超过 30 秒仍等待、遥控键未释放、持续运行、有限日志、通信/
时序/温度故障、双轮禁能、故障锁止和正常停机后的下一次启动。
